# Можливості

## Можливості проєкту

### У кожному конвеєрі та на кожній панелі

- JSON, SARIF 2.1.0 і textfile для node-exporter несуть однакові знахідки, тож сканування коду, Prometheus та Alertmanager бачать те саме, що й людина. Див. [виходи](../how-to/outputs.md).
- GitHub Action перевіряє корінь образу контейнера без його запуску та вивантажує SARIF із підсумком завдання. Див. [CI](../how-to/ci.md).
- Кожен вид збою має власний код виходу, тож конвеєр відрізняє хост із порушеннями від зламаного набору правил чи нечитабельного входу.

### Збирайте раз, оцінюйте будь-де

- Збір фактів і їхня оцінка — окремі кроки: збережіть один документ фактів із хоста, а потім оцінюйте його за довільною кількістю політик, на іншій машині, пізніше, без доступу до хоста. Див. [збирачі](../how-to/collectors.md).
- Один і той самий запуск перевіряє живий хост, змонтовану кореневу файлову систему з `--root` або середовище образу контейнера з `--image-config`, тож еталонний образ перевіряють до випуску.
- Збирачі працюють паралельно, а кожен файл, команда й відповідь мають обмеження розміру та часу, тож завислий монтований NFS чи величезний журнал ніколи не зупинить запуск.
- Збережений документ пам’ятає, коли його зібрано: факти, що застарівають, як-от запущені процеси, спливають, а їхні правила повідомляють `Not run`, а не оцінюють учорашній хост.

### Хост і кожен контейнер за один запуск

- `--containers` знаходить кожен запущений контейнер, зокрема вкладені, і перевіряє кожен зсередини з його власними просторами імен, мітками AppArmor і можливостями (capabilities), тож контейнер оцінюють таким, яким він справді працює. Див. [контейнери](../how-to/collectors.md#containers).
- Знахідка, спільна для багатьох контейнерів, — це один блок, що їх перелічує, а контейнери одного образу оцінюють як один.
- Файл із порушенням, який контейнер не змінював, пов’язують з його образом і кроком збірки для виправлення, а файл, змінений під час роботи, — це власний дрейф контейнера.
- Перевірки лише для хоста, як-от ядро, завантажувач і обладнання, у контейнерах відступають, а не провалюються.

### Налаштування оцінюють так, як їх застосовує програма

- В OpenSSH запитують його власні дійсні налаштування, раз глобально й раз для кожного облікового запису, тож блок `Match`, що знову вмикає вхід за паролем для одного користувача, буде знайдено, і розбирач конфігурації не можна обманути. Див. [sshd](../how-to/sshd.md).
- Права sudo та `Defaults` беруть від самого sudo, класичного й sudo-rs, з розв’язаними включеннями, псевдонімами та групами, а рядок sudoers, який sudo мовчки пропускає як зламаний, повідомляють.
- Стеки PAM, `login.defs`, якість паролів і обмеження ресурсів читають у порядку та за пріоритетом, які використовують їхні бібліотеки, тож оцінюють той рядок, що перемагає. Див. [автентифікація](../how-to/auth.md).
- Налаштування ядра та списки заборонених модулів беруть із `sysctl` і `modprobe`, коли вони доступні, а в іншому разі з їхніх каталогів фрагментів у тому самому порядку, тож змонтований образ оцінюють як завантажений хост.
- Режим файлу журналу оцінюють відносно того, що його перестворює: журнал, який logrotate знову відкриє з безпечними дозволами, не є знахідкою, знахідкою є його правило ротації.

### Дозволи на файли, що мають значення, а не кожен біт

- Файли, що надають root, містять хеші паролів чи ключі хоста або лежать у `PATH`, залишають лише для root, і кожен каталог над програмою з set-user-ID також перевіряють, бо доступний для запису батьківський каталог рівнозначний доступній для запису програмі. Див. [файли](../how-to/files.md).
- Домашній каталог кожного користувача, `~/.ssh` і авторизовані ключі перевіряють ззовні: файл ключів із записом для всіх, короткий RSA чи ключ DSA, домашній каталог, до якого можуть заходити інші.
- Монтування, що шанують біти set-user-ID, файли пристроїв або програми там, де пишуть усі користувачі, називають як в `/etc/fstab`, так і в поточному змонтованому вигляді.
- Облікові записи перевіряють разом у `passwd`, `shadow` і `group`: другий root, повторене ім’я чи ID, обліковий запис без пароля.

### Кожна знахідка справжня

- Правило провалюється лише на ризику, ніколи на самій наявності: згенерований модуль snap, власне середовище образу контейнера чи шлях лише для читання, що належить root, є нормою для свого власника й не підіймають тривоги. Див. [книгу правил](../how-to/rule-book.md).
- Те, чого запуск не зміг перевірити, пояснює причину: `Not run` називає відсутню привілею, `Unknown` означає, що бракує факту, який мав би існувати, а програма, що не встановлена, — це просто нічого перевіряти.
- Набір правил називає хости, для яких його написано, тож на будь-якому іншому хості його правила відповідають «не застосовується» і не впливають на рейтинг. Див. [правила](../how-to/rules.md).
- Там, де стандарт допускає, що хосту щось потрібно, правило це не чіпає: модуль ядра, що використовується, overlay там, де працюють контейнери, squashfs там, де працюють snap, ніколи не просять заблокувати.
- Процедура, яку не доводить жоден факт, — це ручне правило: його показано людині для перевірки й ніколи не зараховано як пройдене.

### Виправлення, які він робить сам, через інструменти, що ними володіють

- `systemlint fix` вносить виправлення, які друкує звіт, на живому хості або в кореневій файловій системі образу з `--root`, і спершу питає; другий запуск нічого не змінює. Див. [виправлення](../how-to/rules.md#remedies).
- Кожне виправлення проходить через інструмент, що володіє налаштуванням: `sysctl --load` після файлу фрагмента, `visudo --check` перед встановленням рядка sudoers, `systemctl mask`, `dockerd --validate` перед перезапуском Docker.
- Виправлення лише забирає доступ: знімає біти дозволів, віддає файл root, коментує рядок, що надає доступ або блокує модуль, тож набір правил, якого ви не писали, ніколи не відкриє хост.
- Рядок, змінений після перевірки, модуль ядра, що використовується, і єдиний авторизований ключ облікового запису залишаються недоторканими, тож виправлення ніколи не позбавить вас доступу.

### Захист ядра та процесора за звітом працюючого ядра

- Вади процесора, які працююче ядро повідомляє як не пом’якшені, і налаштування ядра, що віддають непривілейованим користувачам розкладку пам’яті, адреси ядра чи додаткову поверхню атаки, — кожне є знахідкою.
- Модулі ядра для рідкісних файлових систем, протоколів і пристроїв, що завантажуються на вимогу, знаходять серед модулів, постачених для кожного встановленого ядра, а контролер USB, що довіряє кожному новому пристрою, повідомляють. Див. [модулі ядра](../how-to/services.md#kernel-modules).
- Правила аудиту оцінюють за тим, що вони записують, на диску й завантажені, а не за написанням одного стандарту, тож рівнозначне правило, записане інакше, проходить. Див. [правила аудиту ядра](../how-to/services.md#kernel-audit-rules).
- Незавантажений AppArmor, меню GRUB, яке може редагувати будь-хто, аварійна оболонка без пароля та дампи пам’яті привілейованих програм — кожне є знахідкою.

### Що хост відкриває в мережу

- Сокети, що слухають за межами loopback, зіставляють зі службами, які відповідають кожному, хто до них дістанеться, як-от відкритий API Docker, memcached через UDP чи `cups-browsed`, з програмою, що тримає кожен порт. Див. [сокети, що слухають](../how-to/services.md#listening-sockets).
- Брандмауер оцінюють за тим, що він робить, а не за тим, що він каже: ланцюжки nftables проходять через кожен перехід, щоб з’ясувати, чи відкидають що-небудь, надіслане хосту, і встановлений, але вимкнений ufw називають.
- Системну службу, що слухає порт, який ядро може віддати вихідному з’єднанню, виявляють до того, як вони зіткнуться під час завантаження.
- Redis і MongoDB, відкриті без пароля, спільнота SNMP, яку може вгадати будь-хто, Postfix, що каже стороннім, які адреси існують, і сервери telnet, rsh, TFTP та NIS — кожне є знахідкою.
- З `--network` сервери імен питають, чи розв’язують вони для цього хоста, а сертифікати отримують, щоб виявити спливання строку та зламану довіру, із часовими обмеженнями, повторами й проксі зі середовища. Див. [мережеві зонди](../how-to/collectors.md#network-probes).

### Знахідки, які прочитає людина, конвеєр і екранний читач

- Кожне порушене правило — один блок: рівень, оцінка від 0.0 до 9.9, назва, чому це важливо, кожен уражений суб’єкт і одне виправлення нумерованими кроками, найгірше — першим. Див. [правила](../how-to/rules.md).
- Рейтинг від S до F і по одному лічильнику в рядку завершують запуск і відділяють правила, які ще можна ввімкнути, від тих, яким на хості нічого перевіряти.
- `--plain` друкує один рядок, розділений табуляцією, на кожну знахідку — для `grep`, `awk` та екранних читачів, а колір ніколи не несе зміст сам і вимикається за `NO_COLOR`, `TERM=dumb` чи в конвеєрі.
- Лічильники та розміри групуються й масштабуються так, як їх записує локаль читача.

### Секрети та впроваджений код у кожному середовищі

- Середовища системних файлів, файлів модулів, запущених служб, контейнерів і образів переглядають на облікові дані, впровадження коду через `LD_PRELOAD`, вимкнені перевірки TLS і порожній чи відносний елемент у `PATH`. Див. [середовища](../how-to/env.md).
- Кожне значення замінюють хешем із ключем до того, як воно потрапить до плагіна, документа фактів чи звіту, тож сканування ніколи нікуди не копіює секрет.
- Паролі відкритим текстом у `~/.netrc`, довіру `.rhosts`, яку шанує встановлений rsh, і читабельні конфігурації PostgreSQL, Squid та CUPS повідомляють там, де до них можуть дістатися інші користувачі.

### Диски, що відмовляють, і повні файлові системи до того, як вони покладуть хост

- Диски оцінюють за їхніми власними перевірками стану: збої та знос NVMe й ATA SMART, масиви програмного RAID, що втратили учасника, помилки пристроїв Btrfs і датчики температури зі спрацьованою тривогою.
- Майже повні файлові системи, таблиці файлів і асинхронного вводу-виводу ядра біля свого ліміту та налаштування віртуальної пам’яті, що зупиняють записувачів або рано вичерпують пам’ять, повідомляють до того, як наступний запис зазнає невдачі.
- Служби, що досі виконують код, який оновлення замінило на диску, оновлення, що набувають чинності лише після перезавантаження, і збійні модулі перелічено зі службою для перезапуску. Див. [запущені служби](../how-to/services.md#running-services).
- Вимкнену синхронізацію часу чи без названого сервера та журнал, що нічого не зберігає між перезавантаженнями, виявляють до того, як зіпсуються журнали й сертифікати.

### Правила, що посилаються на стандарти, яким вони відповідають

- Правила мають тегами контролі CIS Ubuntu Linux 26.04, DISA STIG, CIS Controls v8, NIST SP 800-53 і 800-171, PCI DSS 4, ISO 27001:2022, HIPAA та базових рівнів dev-sec, тож `--tags cis`, `--tags 'cis-ubuntu-26.04:5.2.*'` чи `--tags pci-dss` запускає один стандарт або один його розділ. Див. [правила](../how-to/rules.md).
- Правило, що відповідає тесту Lynis, називає його, тож команда, що переходить із Lynis, зберігає свої опорні точки.
- Там, де два стандарти суперечать один одному, як примусова зміна паролів проти NIST SP 800-63B, запуск повідомляє один конфлікт і не провалює хост за жодною з них, а `--prefer 'cis-ubuntu-26.04:*'` дає одному стандарту перемагати в кожному конфлікті. Див. [суперечливі стандарти](../how-to/rule-book.md#conflicting-standards).
- Поріг, який обирає стандарт, за замовчуванням дорівнює числу цього стандарту й змінюється через `--var`, а виняток із датою спливання заглушує знахідку, яку ви приймаєте, доки не настане строк.

### Безпечно запускати від root на хості, якому ви не довіряєте

- Кожен шлях читають усередині кореня, що перевіряється, тож символьне посилання в недовіреному образі ніколи не змусить сканування читати власні файли хоста.
- Кожен плагін — окрема статична програма, що лише перетворює байти, прочитані ядром, на факти: вона не відкриває файлів, не запускає команд і не торкається мережі. Див. [протокол](../how-to/protocol.md).
- Плагіни, збирачі та набори правил завантажують лише з каталогів, що належать root або вам і доступні для запису нікому іншому, а збирач, записаний просто у файлі конфігурації, не може запускати команду.
- Ніщо не залишає хост, доки цього не попросить `--network`.

## Успадковано від B19 / Ubuntu

### Постійний APT-кеш між збираннями

- Кеші пакетів та індексів APT зберігаються між збираннями через кеш-монтування BuildKit із ключем за серією Ubuntu та архітектурою.
- Повторні збирання використовують уже завантажені пакети замість нового завантаження.
- Необов’язковий LAN-проксі кешування APT, вмикається змінною `M6E_APT_CACHE_HOST`.

### Керування службовими процесами зі спрямуванням журналів (b19-exec)

- Тривалі процеси (демони, сервери) мають stdout і stderr, автоматично спрямовані крізь структурований журналізатор.
- Кожен сигнал доходить до служби рівно один раз, тож `docker stop` плавно її завершує, а останні рядки журналу зберігаються.
- Рівні журналування для потоків stdout і stderr налаштовуються незалежно один від одного.
- Кілька демонів ділять один контейнер: кожен рядок позначено його демоном, вони зупиняються у зворотному до запуску порядку, а збій обовʼязкового демона зупиняє контейнер, щоб спрацювала політика перезапуску.
- Режим passthrough передає власний журнал служби збирачеві байт у байт, тож парсери, зроблені для цього демона, далі збігаються.

### Кешовані завантаження артефактів із перевіркою цілісності (b19-fetch)

- Усі зовнішні завантаження проходять крізь трирівневий кеш: локальний каталог `.fetch/`, постійний кеш BuildKit, а потім upstream через aria2c із до 16 з’єднань.
- Необов’язкова перевірка SHA-512 на кожному рівні; невідповідність хеша викликає перехід на наступний рівень, а не збій.
- Режим offgrid повністю блокує всі завантаження та швидко падає з виразною помилкою при промаху кешу.
- Підтримується near-cache-проксі для LAN-збирань, що йдуть через кешувальний проксі.

### Вимірюване виконання команд зі звітуванням про збої (b19-run)

- Будь-яку команду можна обгорнути, щоб отримати автоматичний вимір тривалості та звіт про успіх чи збій.
- Успішний вивід видно лише на вищих рівнях детальності; вивід при збої показується завжди.
- У режимі debug вивід команди транслюється наживо, а не буферизується.

### Одноразова ініціалізація (bootstrap.d)

- Одноразові завдання налаштування (міграції бази даних, створення адміністратора, ініціалізація каталогів) виконуються лише під час першого запуску контейнера.
- Автоматична ідемпотентність: завершені скрипти ніколи не запускаються повторно, навіть між перезапусками контейнера.
- Невдалі скрипти повторюються при наступному запуску; успішні лишаються заблокованими.
- Стан можна скинути очищенням тому, що запускає повний повторний bootstrap.
- Похідні образи додають власні init-скрипти, просто поклавши їх у каталог.

### Модульні хуки збирання (build.d)

- Уся логіка збирання образу живе в пронумерованих shell-скриптах, а не в inline-командах `RUN` Dockerfile.
- Хуки організовано у фази `pre/on/post`, і вони автоматично виявляються за ім’ям етапу, переданим `build-stage`.
- Зарезервована область `always/{pre,post}` обрамляє кожен етап, як би він не називався, тож наскрізне налаштування пишеться один раз, а не для кожного етапу.
- Успадковувані хуки автоматично поширюються на похідні образи через накладання шарів Docker — похідні безкоштовно отримують логіку збирання батька.
- Неуспадковувані хуки вичищаються після виконання, щоб не просочувалися в пізніші етапи.

### Скомпрометовані центри сертифікації позбавлено довіри раніше за upstream

- Сертифікати, перелічені за відбитком SHA-256, вилучаються із системного сховища довіри під час збирання, ще до того, як дистрибутив випустить власне виправлення.
- Один список обслуговує весь родовід образів, а `b19-ca-distrust bundle` урізає за ним будь-який вбудований набір PEM.
- Постачається з недовірою до проміжних сертифікатів eMudhra, чиї закриті ключі можна відновити (жовтень 2026), разом з їхніми перехресними підписами та кореневими сертифікатами.
- Похідні образи додають відбитки однією змінною або одним файлом, а `B19_CA_DISTRUST_ENABLED=false` вимикає урізання. [Посібник](https://codeberg.org/b19/ubuntu/src/branch/main/docs/how-to/use-ca-distrust.md)

### Автоматичне визначення кількості CPU (NUMPROCS)

- Доступні CPU визначаються автоматично через downward API Kubernetes, cgroups v2 або резервний `nproc`.
- Виявлена кількість доступна як `NUMPROCS` протягом усього збирання та виконання й використовується для паралельної компіляції, рендерингу шаблонів і запуску тестів.
- Усуває зашиті кількості завдань і гарантує однаковий паралелізм у Docker, Kubernetes і CI.

### Декларативне керування залежностями (b19-deps)

- Метадані зовнішніх залежностей (URL, версія, SHA-512-хеш) зберігаються як прості текстові файли, повністю окремо від скриптів збирання.
- Підтримуються завантаження для конкретних архітектур, багатоверсійні серії та вкладені шляхи компонентів.
- Залежності автоматично виявляються під час розбору Makefile — додайте файли в потрібний каталог, і збирання їх підбере без ручних оголошень.
- `make fetch` завантажує все наперед для офлайн-збирань; підняття версії запускає автоматичний повторний fetch та оновлення хешів.

### Підключована система запуску (entrypoint.d)

- Кожен запуск контейнера проходить крізь послідовність пронумерованих хуків: налаштування сигналів, завантаження секретів, виявлення CPU, перевірка портів, рендеринг шаблонів, bootstrap, старт служби.
- Окремі команди (`docker run img command`) автоматично оминають частину ланцюга запуску та виконуються безпосередньо.
- Окремі хуки чи весь entrypoint можна пропустити під час виконання через змінні середовища, без перебудови образу.
- Похідні образи перевизначають один-єдиний хук (слот 5000), щоб запустити свою службу; решта успадковується.

### Перемикачі функцій для всіх підсистем

- Кожну велику підсистему (entrypoint, healthchecks, bootstrap, тести, секрети, перевірку портів, i18n, shell-хуки) можна вимкнути під час виконання через змінні середовища.
- Окремі хуки entrypoint, bootstrap і перевірок стану можна пропустити за ім’ям, не вимикаючи всю підсистему.
- Перебудова образу не потрібна — перемикачі діють лише в рантаймі.

### Вбудований моніторинг стану (healthcheck.d)

- Перевірка стану у власному для Docker стилі, успадкована всіма похідними образами без додаткової конфігурації.
- Перевірки зовнішнього доступу вмикаються за бажанням: контейнер, який ніколи не звертається до інтернету, не має жодної перевірки, яку може завалити третя сторона, а той, чия робота — інтернет, стає несправним щойно зовнішній світ зникає.
- Працює однаково офлайн і онлайн — перевірки зовнішнього доступу самі вимикаються в режимі offgrid.
- Додати перевірку означає покласти скрипт у каталог, а не писати конфігурацію Docker.
- Важкі перевірки або перевірки з обмеженням частоти запитів виконуються щогодини у фоні, тож повільне сканування ніколи не вичерпує час перевірки стану й не витрачає ліміт запитів.

Див. [use-healthcheck.d](https://codeberg.org/b19/ubuntu/src/branch/main/docs/how-to/use-healthcheck.d.md) щодо переліку перевірок, нумерації слотів і налаштувань.

### Багатомовний вивід shell (b19-i18n)

- Усі повідомлення журналу та вивід скриптів, видимі користувачеві, перекладаються через GNU gettext.
- З коробки поставляються англійська, іспанська (`es_CL`) та українська (`uk_UA`).
- Похідні образи автоматично успадковують усі батьківські переклади; перекладати потрібно лише нові чи перевизначені рядки.
- Переклади компілюються під час збирання без накладних витрат у рантаймі.

### Відстеження лініжу образу

- Кожен образ записує свої метадані збирання (namespace, проєкт, версія, базовий образ) у файл лініжу під час збирання.
- Похідні образи зчіплюють лініж зі свого батька, утворюючи повний ланцюг походження від бази до поточного.
- Весь ланцюг лініжу записується в журнал під час запуску (на детальній verbosності, рівень debug) і його можна будь-коли прочитати з файла, тож легко простежити, з чого зібрано запущений контейнер.

### Структуроване журналування з фільтром за рівнем (b19-log)

- Увесь вивід контейнера проходить крізь журналізатор із рівнями й чотирма порогами: error, warn, info, debug.
- Повідомлення нижче налаштованої детальності мовчки відкидаються, тож робочі журнали лишаються чистими.
- Кольори автоматично визначають підтримку терміналу й шанують `NO_COLOR=1`.
- Придатне до конвеєра: вивід команди можна спрямувати крізь журналізатор, щоб застосувати фільтр рівнів і теґи.
- `B19_LOG_FORMAT=json` перетворює кожен рядок на JSON-об’єкт, який конвеєр журналів читає без парсера; власні рядки служби теж стають полями, а оригінальний рядок зберігається поруч із ними.

### Контейнер без прав root за замовчуванням

- Контейнер працює від користувача без прав root (`ubuntu`, UID/GID 1000), і всі робочі файли належать цьому користувачеві.
- Двоетапне збирання відокремлює системне встановлення від імені root від налаштування середовища виконання на рівні користувача.
- Ідентичність користувача налаштовується під час збирання, а необов’язковий запуск від root переназначає її на користувача хоста, щоб bind-монтування зберігали власника.

### Підтримка ізольованих від інтернету (air-gapped/offline) збирання й виконання

- Єдина змінна середовища (`B19_OFFGRID_MODE=Y`) відтинає весь доступ до інтернету під час збирання та виконання.
- Під час збирання: завантаження блокуються, оновлення APT пропускаються, keyscan SSH пропускається. Усі артефакти мають надходити з рівнів кешу.
- У рантаймі: мережні перевірки стану автоматично пропускаються зі здоровим результатом, тож контейнери лишаються зеленими в ізольованих мережах.
- Списки пакетів APT можна зняти у знімок і вставити для повністю офлайн-збирань образу.
- LAN-служби (кешувальні проксі, реєстри) лишаються досяжними — offgrid блокує інтернет, а не всю мережу.

### Ін’єкція оверлеїв під час виконання

- Файли конфігурації чи даних можна вставити під час запуску контейнера, задавши в `B19_OVERLAY` ім’я каталогу.
- Вміст оверлея рекурсивно копіюється в корінь контейнера, перезаписуючи наявні файли — перебудова образу не потрібна.
- Пропускається в незмінному режимі, що запобігає модифікації під час виконання образів, заблокованих для продакшну.

### Відтворюваний базовий образ (зафіксований за digest)

- Базовий образ Ubuntu зафіксований за SHA-256-digest, а не за тегом, що гарантує детерміновані збирання.
- Підтримуються кілька серій Ubuntu (resolute, noble, jammy) на вибір під час збирання.
- Дзеркала APT налаштовуються окремо за архітектурою для LAN-дзеркал або ізольованих середовищ.

### Перевірка портів

- Усі змінні середовища `*PORT*` перевіряються під час запуску за списком заборонених портів WHATWG і за привілейованими портами (\<1024).
- Завчасно ловить хибні налаштування на кшталт `HTTP_PORT=22`, перш ніж служба непомітно впаде.
- Можна вимкнути під час виконання без перебудови образу.

### Уніфіковане сімейство ранерів життєвого циклу

- Вісім ранерів із пронумерованими хуками покривають повний життєвий цикл контейнера: запуск, healthchecks, тести, bootstrap, хуки збирання, бенчмарки, звіти та shell-сеанси.
- Усі ранери поділяють той самий патерн: покладіть пронумерований скрипт у каталог — він автоматично виявиться й виконається.
- Скрипти з різних шарів образу зливаються — upstream- і downstream-хуки співіснують без конфліктів.
- Кожен ранер має власну семантику збоїв: перервати при помилці (entrypoint, bootstrap), продовжити й порахувати збої (healthchecks, тести), завжди завершуватися успішно (звіти).

### Автозавантаження Docker-секретів (secrets)

- Файли Docker-секретів автоматично виявляються та перетворюються на змінні середовища під час запуску.
- Імена файлів у точковій нотації відповідають змінним середовища у верхньому регістрі (`b19.npm.registry_host` стає `B19_NPM_REGISTRY_HOST`).
- Обов’язкові секрети можна оголосити за ім’ям; контейнер відмовляється стартувати, якщо бракує хоч одного.
- Наявні змінні середовища мають пріоритет над значеннями, похідними від секретів.
- Секрети також доступні в інтерактивних shell-сеансах і healthchecks.
- Не-UTF-8/бінарні секрети (ключі, DER-блоби, gzip-тарболи) **не** експортуються як змінні середовища: Bash обрізає їх на першому NUL, а випадкові байти ламають будь-який інструмент, що читає середовище як UTF-8 (наприклад, `minijinja --env`, яким шаблонізують конфіги). Вони лишаються на диску в `/run/secrets/<name>` для читання як файлів — що й так єдиний правильний спосіб споживати бінарний секрет.

### Хуки інтерактивної shell (shell.d)

- Сеанси `docker exec bash` автоматично завантажують Docker-секрети та будь-які власні хуки, додані похідними образами.
- Хуки зливаються через накладання шарів Docker, тож успадковане та проєктне налаштування shell співіснують.

### Плавна обробка сигналів

- PID 1 — це `catatonit -g`, який прибирає процеси-зомбі та переспрямовує сигнали всій групі процесів.
- Налаштовуваний набір Unix-сигналів (TERM, INT, HUP, USR1, USR2 тощо) перехоплюється та переспрямовується кожному процесу служби, і вони зупиняються у зворотному до запуску порядку.
- `docker stop` чисто завершує службу без осиротілих процесів і втрачених сигналів.

### Шаблони конфігурації Jinja2 (minijinja-cli)

- Рендеринг шаблонів, сумісний із Jinja2, і під час збирання, і під час запуску контейнера.
- Покладіть файл `.j2` будь-де в каталозі застосунку — його виявлено під час збирання й відрендерено при кожному запуску з усіма доступними змінними середовища.
- Рендеринг під час виконання паралельний і автоматичний — похідні образи отримують його без жодної конфігурації.
- Незмінний режим (`B19_IMMUTABLE=Y`) заморожує файлову систему до стану на момент збирання, пропускаючи весь рантайм-рендеринг.

### Вбудований тестовий фреймворк (test.d)

- Тести виконуються всередині запущеного контейнера через `make test` чи `docker exec`.
- Автоматично чекає проходження healthchecks перед виконанням.
- Без залежності від тестового фреймворку — тести це звичайні shell-скрипти з кодами виходу, а невдала перевірка називає, що очікувала і що знайшла.
- Підтримуються шаблони Jinja2 у тестах, що зручно для перевірки під час виконання значень, зафіксованих під час збирання.
- Продовжує після збоїв і звітує загальну кількість; ніколи не ховає часткові результати.

### Ніщо не зависає назавжди

- Кожен крок запуску, тестування та разової команди має обмеження в часі, тож заблокований інструмент гучно падає, а не зупиняє розгортання чи запуск CI.
- Завмерлі завантаження перериваються, а повільні будь-якого розміру завершуються.
- Нестабільний виклик можна повторювати з наростаючою паузою одним прапорцем, без рукописного циклу.
- Необов’язковий перезапуск перетворює сервіс, що застряг у несправному стані, на контейнер, який відновлює політика перезапуску.

Див. [use-timeouts](https://codeberg.org/b19/ubuntu/src/branch/main/docs/how-to/use-timeouts.md) щодо параметрів, типових значень і перевизначень.

### Попередньо встановлені службові інструменти

- `mold` як типовий лінкер (можна вимкнути).
- `fd` для пошуку файлів, `minijinja-cli` для рендерингу шаблонів.
- `aria2c` для багатоз’єднаних завантажень, `catatonit` як PID 1 для прибирання зомбі.
- Інструменти паралельного стиснення: `pbzip2`, `pigz`, `pixz`.
- Інструменти gettext для компіляції i18n, `cURL` для мережевих операцій.

### Шляхи XDG Base Directory

- Стандартні XDG-шляхи (`XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`) задаються в домашньому каталозі застосунку.
- Усі шляхи доступні користувачеві без прав root для запису, без підвищення привілеїв.
